# 비용 방어 — 3층 구조와 남은 구멍

작성: 2026-08-09 · 상태: **2층까지 구현 · 3층 미구현**
발견 경위: 오너가 *"지웠다 다시 쓰기를 반복하면 토큰값이 장난 아니겠는데?"* 라고 물어 숫자를 넣어보다 드러났다.

> **한 줄 요약:** 아이별 한도만 있었다. 아이를 늘리면 그대로 배수가 됐고, **계정을 늘리면 지금도 배수다.**

---

## 1. 왜 이 문서가 필요한가

한도는 **한 층만으로는 아무것도 못 막는다.** 아래를 막으면 위로 우회한다.

```
① 아이 한 명이 몰아 쓴다        →  아이별 한도가 막는다      ✅ 예전부터
② 아이를 늘려 우회한다          →  계정 총량이 막는다        ✅ 2026-08-09 추가
③ 계정을 늘려 우회한다          →  전역 상한이 막아야 한다    ❌ 없음
```

②를 오늘 막았다. **③은 아직 열려 있다.**

---

## 2. 오늘 무엇을 고쳤나

### 문제

`quota.LIMITS` 는 **아이 한 명당** 한도였다. 프로필은 최대 4개까지 만들 수 있으므로 **최악이 4배**였다.

| | 아이 1명 | 아이 4명 (상한) |
|---|---|---|
| 그림일기 (gen+continue) | 470원/일 · 월 14,100원 | 1,880원/일 · **월 56,400원** |
| 영상 정밀분석 | 340원/일 · 월 10,200원 | 1,360원/일 · **월 40,800원** |

그리고 검사가 찍던 비용 표는 **아이 1명 값만** 보여주고 있었다 — 사람이 보고 지나가라고 만든 자리인데 **실제보다 작은 숫자**였다.

### 고친 것 — `ACCOUNT_LIMITS` 신설

아이별 한도는 그대로 두고, **계정 전체 총량**을 한 겹 더 걸었다. 아이가 몇 명이든 총액이 고정된다.

| 종류 | 아이별 | 계정 총량 | 1회 원가 | 계정 최악 |
|---|---|---|---|---|
| `diary_gen` | 5 | **6** | 40원 | 240원/일 |
| `diary_continue` | 3 | **3** | 90원 | 270원/일 |
| `analyze_deep` | 20 | **30** | 17원 | 510원/일 |
| | | | **합계** | **1,020원/일 · 월 30,600원** |

**월 56,100원 → 30,600원.**

### 🔴 조이는 쪽에도 위험이 있다

*"막으면 안전하다"* 가 아니다. **아이가 그림을 못 그리는 것**도 사고고, 그건 **조용히 일어나 아무도 신고하지 않는다.**

그래서 숫자를 정할 때 정상 사용을 먼저 쟀다:

| 종류 | 정상 사용 | 여유 |
|---|---|---|
| `diary_gen` 6 | 아이 4명 각자 일기 1편 = 4회 | 2회 (다시 그리기) |
| `analyze_deep` 30 | 아이 4명 각자 새 영상 7~8편 | 넉넉 |

`analyze_deep` 을 20으로 조이는 안도 있었으나(월 10,200원), **한 아이가 하루 20편을 보면 나머지 셋이 아예 못 보게 되어** 30으로 정했다(오너 확정). 아낀 돈은 계정당 월 5,100원인데 대가가 더 확실했다.

⚠️ **이 '정상 사용'은 추정이다.** 아이가 실제로 몇 번 다시 그리는지, 하루에 새 영상을 몇 편 여는지는 **아직 아무도 재보지 않았다.**
→ 막히는 사례가 보이면 **좁히지 말고 넓히는 쪽**으로 조정할 것.

### 장치

`_validate_limits()` 가 양쪽 끝을 다 막는다 — 값을 잘못 넣으면 **서버가 아예 안 뜬다.**

| 조건 | 왜 |
|---|---|
| 계정 총량 **< 아이별** → 거부 | 아이 한 명도 자기 몫을 못 쓴다 |
| 계정 총량 **≥ 아이별 × 4** → 거부 | 아이별이 먼저 걸려 아무것도 못 막는다 |

⚠️ 실제로 이 검사가 **내 실수를 잡았다.** 처음엔 *"계정 총량이 아이별보다 크면 무의미"* 라고 조건을 반대로 썼는데, 계정 총량의 목적은 **여러 아이의 합**을 막는 것이라 아이별보다 커도 의미가 있다.

`_verify_quota.py [D-2]` 8건 + 차단 시험(계정 한도 제거 → 잡힘). **대조군을 먼저** 확인한다 — 첫째가 자기 몫 5회를 다 쓸 수 있는지부터 본다.

## 3. 🔴 남은 구멍 — 3층(전역 상한)

**계정을 늘리면 그대로 배수다.** 한도는 계정 하나의 상한만 정할 수 있다.

| 계정 수 | 한 달 최악 |
|---|---|
| 1개 | 30,600원 |
| 10개 | 306,000원 |
| **100개** | **3,060,000원** |
| 1,000개 | 3,060만원 |

### 지금은 왜 괜찮은가

- 실사용자가 **오너 가족뿐**이다
- **회원가입 이메일 인증을 켰다**(2026-08-08) — 계정 100개를 만들려면 실제 이메일 100개가 필요하다
- 우리를 노릴 만큼 알려지지 않았다

### 언제 막아야 하나

🔴 **공개 출시 전.** 알려지는 순간 조건이 바뀐다.

### 무엇을 정해야 하나 (다음에 다시 볼 때)

| # | 질문 | 왜 지금 못 정하나 |
|---|---|---|
| 1 | 전역 일일 상한을 얼마로 | **실사용 데이터가 0이다.** 계정 하나가 실제로 하루 얼마를 쓰는지 모른다 |
| 2 | 상한에 닿으면 어떻게 | 전부 막으면 정상 사용자도 막힌다. 유료 우선? 큐? 알림만? |
| 3 | 어디에 저장하나 | 지금 카운터는 **메모리**다 — Railway 가 재시작하면 0이 된다. 전역이면 DB 가 필요할 수 있다 |
| 4 | 유료 플랜과 어떻게 엮나 | 무료는 좁게·유료는 넓게가 자연스러운데, 결제가 아직 없다(GD-40) |

### 함께 볼 것

- **그림일기 업로드 한도** — `POST /diary/assets` 에는 아직 한도가 **없다**(Storage·DB·egress 어디에도). 같은 시점에 붙일 것.
- **캐시 적중률** — `analyze_deep` 실측 97.2%. 이 값이 떨어지면 비용 가정이 통째로 흔들린다. 재측정 필요.
