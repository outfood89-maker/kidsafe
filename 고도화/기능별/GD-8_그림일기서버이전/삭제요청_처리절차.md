# 삭제 요청 처리 절차 — 부모가 "우리 아이 데이터를 지워주세요"라고 했을 때

*작성 2026-08-07(팀장) · 근거: GD-8b §1-7 · 개인정보 보호법 제21조(파기)*
*⚠️ 법률 자문 아님. 조문 해석과 실행 절차 정리까지가 범위다.*

> **이 문서는 무엇인가**
> 삭제 요청을 받은 **오너가 그대로 따라 실행하는 매뉴얼**이다. 요청 범위별로 무엇이 어떻게 지워지는지,
> 무엇을 확인해야 "다 지웠다"고 답할 수 있는지, 그리고 **아직 못 하는 것이 무엇인지**를 적는다.
>
> 🔴 **아직 못 하는 것을 숨기지 않는다.** 이 문서의 가치는 "다 된다"가 아니라 **"어디까지 되고 어디부터 안 되는지"** 다.

---

## §0. 처리 기한

법 제21조는 **"지체 없이"** 파기하도록 정한다. 숫자로 못박는다:

| 단계 | 목표 |
|---|---|
| 접수 확인 회신 | **1영업일 이내** |
| 신원 확인 완료 | 접수 후 **3영업일 이내** |
| 실행 + 확인 + 결과 회신 | 신원 확인 후 **5영업일 이내** |
| 전체 | **10영업일 이내** |

⚠️ 기한을 못 지킬 사정이 생기면 **그 사실과 사유를 먼저 알린다.** 침묵이 가장 나쁘다.

---

## §1. 6단계 절차

### ① 접수
- 경로: `Account.jsx:81` 안내 이메일 (현재 유일한 창구 — 앱 내 셀프 삭제 버튼 없음)
- 접수 즉시 **§5 기록표**에 한 줄 남긴다.

### ② 신원 확인 — 🔴 건너뛰지 말 것
- **가입 이메일 주소로 회신을 받는 방식**으로 확인한다. 요청 메일의 발신 주소가 가입 주소와 같아야 한다.
- 다르면: 가입 주소로 확인 메일을 보내 회신을 받는다.
- ⚠️ **이 단계를 생략하면 남의 아이 데이터를 지워주는 사고가 난다.** 삭제는 되돌릴 수 없다.

### ③ 범위 확인
부모에게 **어디까지** 지울지 확인한다. 아래 §2 표를 그대로 보여줘도 된다.

### ④ 실행
§2 표의 해당 행을 실행한다.

### ⑤ 확인 — §3 쿼리 3종을 **전부** 통과해야 한다
하나라도 0이 아니면 **아직 끝난 게 아니다.** 회신하지 말고 §4를 본다.

### ⑥ 회신 + 기록
- 무엇을 언제 지웠는지 회신한다. **§6의 "아직 못 하는 것"을 함께 알린다.**
- §5 기록표를 완성한다.

## §2. 요청 범위별 실행 방법

| 요청 | 실행 | 그림일기는 어떻게 되나 | 상태 |
|---|---|---|---|
| **일기 1편** | 앱: 부모 앨범 수정모드에서 삭제 | 행 삭제 → 트리거가 명세서 작성 → 파일 삭제 | ✅ |
| **그 아이 일기 전부** | `DELETE /diary/entries?profileId=...` | 행별로 트리거가 돌아 전량 삭제 | ✅ |
| **프로필 1개 통째로** | 앱: 프로필 삭제 / API `DELETE /profiles/{id}` | **FK cascade → 일기 행 삭제 → 트리거 → 파일 삭제.** 별도 조치 불필요 | ✅ |
| **계정(회원 탈퇴)** | 🔴 **엔드포인트 없음 — 오너 수동** (아래) | 아래 순서대로 하면 자동 수렴 | ⚠️ **부분** |

### 계정 삭제 수동 절차 (엔드포인트 미구현 — 실측 확인 2026-08-07)

Supabase 콘솔에서:

1. **Authentication → Users** 에서 해당 사용자를 찾아 삭제
2. 그러면 자동으로 이어진다:
   ```
   auth.users 삭제
     → profiles 삭제 (schema.sql FK cascade)
       → diary_entries 삭제 (006 FK cascade)
         → 트리거 발동 → diary_deletions 에 명세서 생성
   ```
3. **파일은 아직 안 지워졌다** → 관리자 API 로 큐를 배출한다:
   ```
   POST /diary/admin/sweep      (관리자 토큰 필요)
   ```
4. §3 확인 쿼리를 돌린다.

⚠️ **3번을 빠뜨리면 DB 행은 사라졌는데 Storage 파일이 남는다.** 아무도 도달할 수 없는 상태이긴 하나
   "완전 파기"라고 말하려면 여기까지 해야 한다.

## §3. 확인 쿼리 3종 — 전부 0이어야 끝이다

Supabase → SQL Editor 에서 실행. `<PROFILE_ID>` 를 바꿔 넣는다.

```sql
-- ① 일기 행이 남았나 (기대: 0)
select count(*) as remaining_entries
  from public.diary_entries
 where profile_id = '<PROFILE_ID>';

-- ② 아직 안 지워진 파일이 있나 (기대: 0)
select count(*) as pending_deletions
  from public.diary_deletions
 where state = 'pending';

-- ③ 삭제에 실패해 포기된 게 있나 (기대: 0)
select count(*) as failed_deletions, array_agg(id) as ids
  from public.diary_deletions
 where state = 'failed';
```

| 결과 | 의미 | 조치 |
|---|---|---|
| ① > 0 | 행이 안 지워졌다 | 삭제 실행이 실패한 것. 다시 실행 |
| ② > 0 | 파일이 아직 큐에 있다 | `POST /diary/admin/sweep` 실행 후 재확인 |
| ③ > 0 | 8회 재시도 끝에 포기됐다 | §4 로 |

## §4. 실패 대응

### `state='failed'` 가 나왔을 때

1. 해당 행의 `last_error` 와 `paths` 를 본다:
   ```sql
   select id, entry_id, paths, prefix, attempts, last_error
     from public.diary_deletions where state = 'failed';
   ```
2. Supabase → **Storage → diary-assets** 에서 `prefix` 경로를 찾아 **수동 삭제**한다.
3. 처리했으면 상태를 정리한다:
   ```sql
   update public.diary_deletions
      set state = 'done', done_at = now(), paths = '{}', prefix = null
    where id = '<그 행의 id>';
   ```

### 🔴 백업 복구 사고 대응 — 지운 게 되살아났을 때

백업에서 DB를 복구하면 **지웠던 일기가 되살아난다.** 이때 `diary_deletions` 가 **되살리면 안 되는 목록**이 된다.

```sql
-- 복구 직후 실행 — 명세서에 있는 entry_id 는 이미 '지워진 것'이다. 다시 지운다.
delete from public.diary_entries
 where id in (select entry_id from public.diary_deletions);
```

⚠️ **이 절차가 없으면 부모에게 한 "완전히 지웠습니다"가 거짓말이 된다.**
   그래서 `diary_deletions` 의 `done` 행을 지우지 않는 것이다 — 이 목록이 존재 이유다.

## §5. 기록표 (요청 건마다 한 줄)

| 접수일 | 요청자(가입 이메일) | 범위 | 신원확인일 | 실행일 | 확인쿼리 3종 | 회신일 | 비고 |
|---|---|---|---|---|---|---|---|
| | | | | ①0 ②0 ③0 | | | |

> 이 표를 남기는 이유: 제21조 이행을 **증명**할 수 있어야 한다. 지웠다는 사실 자체는 지워진 데이터로 증명할 수 없다.

## §6. 🔴 아직 못 하는 것 — 회신에 반드시 포함

정직하게 알린다. 숨기면 나중에 더 큰 문제가 된다.

| # | 못 하는 것 | 왜 | 언제 |
|---|---|---|---|
| 1 | **앱 안에서 계정 삭제** | 엔드포인트 미구현(실측 0건). 이메일 요청 → 오너 수동 | 고도화 2층 #10 |
| 2 | **다른 기기 브라우저에 남은 사본** | 아이가 쓰던 다른 기기의 브라우저 저장소는 서버가 도달할 수 없다. 그 기기에서 앱을 열어야 정리된다 | GD-8c |
| 3 | **AI 처리 과정에 남은 흔적** | 그림 생성 시 OpenAI 가 최대 30일 보관(남용 모니터링). 우리가 지울 수 없다 | 처리방침 고지 사항 |
| 4 | **백업본** | 자동 백업에는 삭제 전 상태가 남아 있을 수 있다. 백업 주기가 지나면 사라진다 | §4 복구 절차로 대응 |

### 회신 문안 예시

> 요청하신 데이터를 **○년 ○월 ○일 삭제 완료**했습니다.
> 일기 ○편과 그림·음성 파일이 서버에서 삭제되었으며, 확인 절차를 마쳤습니다.
>
> 다만 아래는 함께 안내드립니다:
> · 아이가 사용하던 **다른 기기의 브라우저**에 사본이 남아 있을 수 있습니다. 그 기기에서 앱을 한 번 열면 정리됩니다.
> · 그림 생성에 사용된 외부 AI 서비스에 **최대 30일간** 처리 기록이 남을 수 있으며, 이후 자동 삭제됩니다.
> · 자동 백업본에는 삭제 이전 상태가 일시적으로 남을 수 있으나, 복구 시 재삭제되도록 조치되어 있습니다.

## §7. 오너의 Supabase 콘솔 직접 열람 규칙

**오너는 service key 로 아이 데이터 원문을 볼 수 있다.** 이건 기술적으로 막지 않았다(GD-8b §1-8: E안 채택 — 최소권한 + 비공개 버킷 + 짧은 서명 URL + **열람 규칙 문서화**).

막지 않은 이유는 정직하게 적어둔다:
- RLS 를 걸어도 `service_role` 은 우회하며, **콘솔이 곧 그 권한**이다. 기술로 막는 척만 하게 된다.
- 컬럼 암호화(C안)는 키를 서버가 쥐고, 그 서버도 오너 것이라 **사실상 여전히 본다.**
- E2EE(D안)는 진짜로 막지만 비용이 매우 크고, 부모 리포트·검수 같은 기능이 성립하지 않는다.

**그래서 규칙으로 관리한다:**

1. **장애 대응·삭제 요청 처리 시에만** 연다. 궁금해서 열지 않는다.
2. 열었으면 **아래 표에 기록한다.**
3. 아이 대화·일기 원문을 **다른 곳에 복사하지 않는다.**

| 날짜 | 사유 | 열람 범위 | 비고 |
|---|---|---|---|
| | | | |

> 🔴 이 규칙은 기술이 아니라 약속이다. 약속이 지켜졌는지는 이 표로만 확인된다.
> 상용화 단계에서는 **접근 로그 자동 기록**으로 승격해야 한다(고도화 S5 감사 로그 확대).

## 🔴 미해결 — 고아 자산 (2026-08-07 실사고로 발견)

**증상**: `diary_entries` 0건인데 `diary_assets` 1건 + Storage 파일 1개가 남았다.

**원인**: 이사 엔진(GD-8c)은 **자산 먼저, 엔트리 나중**으로 올린다(설계 ②).
그래야 *"서버에 엔트리가 있다 = 자산까지 완료"* 가 참이 된다. 그런데 그 사이에 끊기면
**엔트리 없는 자산**이 남는다.

**왜 저절로 안 지워지는가**

| 청소 경로 | 고아를 지우는가 |
|---|---|
| `diary_entry_after_delete` 트리거 | ❌ `diary_entries` 삭제가 방아쇠인데 그 행이 없다 |
| `POST /diary/admin/sweep` | ❌ `diary_deletions`(삭제 명세서)만 훑는다 |
| 프로필 삭제 cascade | ⭕ 프로필을 지우면 함께 사라진다 |

**설계 의도**: 다음 회차에 같은 엔트리를 재시도 → 자산 경로가 결정적이라 덮어쓰기 →
엔트리가 붙으면 고아 아님. **즉 고아는 원래 일시적이어야 한다.**

**그런데 영구화되는 경로가 있다**
1. 엔트리 저장이 **영구 실패**하는 경우(형식 오류 등) — 5회 뒤 자동 회차에서 제외된다
2. 사용자가 그 사이 **로컬 일기를 지운 경우** — 재시도할 원본이 사라진다
3. 사용자가 **동의를 철회**한 경우 — 이사가 게이트에서 멈춘다

**해야 할 일 (미착수)**
- [ ] 고아 자산 청소기 — `diary_assets` 중 `diary_entries` 가 참조하지 않는 행을
      일정 기간(예: 7일) 뒤 정리. 관리자 sweep 에 붙이는 것이 자연스럽다.
- [ ] ⚠️ **주의**: 업로드 직후~엔트리 저장 사이의 정상 상태를 지우면 안 된다.
      유예 기간이 반드시 필요하다.
- [ ] 재시도 상한(5회)에 걸린 엔트리를 부모에게 알릴지 결정

> 🔴 이건 삭제 관철(GD-8b)의 사각이다. *"지우면 정말 지워집니다"* 는 지켜지지만,
> **애초에 도달할 수 없는 데이터**는 그 약속의 대상이 아니었다.
