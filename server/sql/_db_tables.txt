# 실제 Supabase DB 의 public 표 전수 + **탈퇴 시 어떻게 되는가** (DB 가 답한 것)
#
# 형식:  표이름|판정      판정 = auth | profiles | none
#   auth      … auth.users 에 on delete cascade 로 직접 매달려 있다
#   profiles  … profiles 를 거쳐 2단으로 지워진다
#   none      … 어떤 FK 로도 안 지워진다 → 코드가 지우거나(report_coach)
#                일부러 남기는 것이어야 한다(_verify_account_delete.py 의 ALLOWED_SURVIVORS)
#
# 🔴 왜 이 파일이 있는가 (2026-08-10 실사고)
#   `_verify_account_delete.py` [C] 는 원래 server/sql/*.sql 만 읽고 cascade 를 **추측**했다.
#   그런데 SQL 파일이 실물의 전부가 아니었다 — care_signals 는 대시보드에서 만들어져
#   파일에 정의가 없었고, 검사는 그 표의 존재조차 몰랐다. 결과: 아이의 위기 신호가
#   프로필 삭제·탈퇴 양쪽에서 남고 있었는데 검사는 "설명되지 않는 표 0개"라고 초록불을 켰다.
#
#   ⇒ 표를 손으로 세지 않게 만든 것까지는 맞았다.
#      틀린 것은 **기계에게 읽힌 원본이 진실인지 의심하지 않은 것**이다.
#   ⇒ 그래서 이제 **DB 에게 직접 묻는다.** 추측이 아니라 pg_constraint 가 답한 값이다.
#
# 🔄 갱신 방법 — 표를 만들거나 지웠거나 FK 를 바꿨으면 반드시 여기도 고칠 것
#   Supabase → SQL Editor:
#
#     with c_auth as (
#       select ch.relname as tbl from pg_constraint con
#       join pg_class ch on ch.oid = con.conrelid
#       where con.contype='f' and con.confdeltype='c' and con.confrelid='auth.users'::regclass),
#     c_prof as (
#       select ch.relname as tbl from pg_constraint con
#       join pg_class ch on ch.oid = con.conrelid
#       where con.contype='f' and con.confdeltype='c' and con.confrelid='public.profiles'::regclass)
#     select t.table_name || '|' ||
#       case when t.table_name in (select tbl from c_auth) then 'auth'
#            when t.table_name in (select tbl from c_prof) then 'profiles'
#            else 'none' end
#     from information_schema.tables t
#     where t.table_schema='public' and t.table_type='BASE TABLE'
#     order by 1;
#
#   ⚠️ 갱신을 잊으면 검사가 양방향으로 걸린다:
#      · SQL 파일엔 cascade 를 적었는데 여기엔 none → **SQL 을 실행하지 않았다**
#      · 여기엔 있는데 SQL 파일이 모르는 표    → **정의를 파일에 안 남겼다**
#
# 최종 갱신: 2026-08-10 (오너 실행 · 31개 · auth 16 / profiles 5 / none 10)
#   · 33개였다가 011 로 backup_checkins_judgeweek · backup_history_judgeweek 를 버려 31개
#   · care_signals 는 010 으로 none → auth 가 되었다
